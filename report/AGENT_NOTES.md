## What this is

`CDE1302_Final_Report_DRAFT.docx` is the draft final report on the mission
demonstration (11 Nov 2026). It is **generated**, not hand-written:

```
report/
├── AGENT_NOTES.md                  this file
├── requirements.txt                Python packages for the two scripts
├── analyse_flights.py              logs -> figures/*.png + data/metrics.json
├── analyse_ulog.py                 PX4 ULogs -> figures/fig_ulog_lanes.png + data/ulog_metrics.json

    ├── flights/<run>/              copies of cde1302/mission/logs/<run>/ (that folder is gitignored)
```

Rebuild from the repo root:

```bash
pip install -r report/requirements.txt
python report/analyse_flights.py
python report/build_report.py
```

**Edit the text in `build_report.py`, not in the .docx.** A rebuild overwrites
the .docx. If the team has already started editing the .docx by hand in Word,
stop regenerating it: make further changes in Word (or by unzipping and editing

IMU facts from the user: `EKF2_MULTI_IMU` = 3 is PX4's default on this board.
The team changed it during intermediate tests. For the demo they kept the
default and set the IMU priorities to IMU0 (BMI088) very high and IMU1
(BMI270) very low, so PX4 falls back to IMU1 only when IMU0 fails. The user's
argument for this (13 Nov, now in §8): the BMI088 is the application-specific
(drone/robotics, vibration-robust) IMU, while the BMI270 is a wearables part, more
prone to vibration and drift. With no compass, accumulated yaw drift has nothing to
be compared against in either instance, so it is never flagged, which makes
auto-switching / equal (default MEDIUM) priorities unsafe. Refs [7] and [8] are the Bosch datasheets.

Ground control points (= localisation tags, §3): the course's search dictionary is
a truncated tag16h5 (IDs 0-21); IDs 22-29 were restored and reserved for GCPs.
`mission/tools/loc_layout.py` places any number of them on any 0.46 m grid node,
so the layout can move if a search tag lands on a planned GCP. The demo used
22-25 + 29 (home). Checked in the demo ULogs (13 Nov): no switch happened in any
of the three flights. The primary gyro stayed the BMI088 and the position and heading
reset counters never changed in flight. `estimator_selector_status` is not logged
under `SDLOG_PROFILE` 161, so this shows that no switch happened, not that one
could not happen.

## Demo-ULog analysis (done 13 Nov 2026)

`report/analyse_ulog.py` (pyulog) reads the logs in place from
`cde1302/mission/px4_logs/` and writes `data/ulog_metrics.json` and
`figures/fig_ulog_lanes.png` (Figure 5). Run it from the repo root after
`analyse_flights.py` (it imports that script's palette).

- **Which log is which:** the FC has no RTC, so the logs have no wall-clock time.
  The script slides PX4 x, y along each run's `trajectory.csv`. The correct pairing
  agrees to 0.6-0.8 cm mean error and every other pairing is off by 0.6 m or more
  (it asserts this). Arm-to-AUTO_LAND time is about 1 s shorter than the
  take-off-to-land-command time (74.6/75.6 s and 35.2/36.1 s). ULog time is
  about mission time minus 1.2 s.
- **Logging rates** (`SDLOG_PROFILE` 161): position and setpoints 10 Hz,
  `trajectory_setpoint`/estimator status 5 Hz, attitude 20 Hz,
  `estimator_states`/raw sensors 1-2 Hz.
- **Eq. 3 holds:** `vehicle_local_position_setpoint` (vx, vy) projected across the
  lane equals −k_p·e_c·min(1, v_max/(k_p·|e|)) to within 1 mm/s in every lane sample
  (with `MPC_XY_P` 1.35). At the worst point the demand is 11-46 % of k_p·e_c.
  Every lane starts with 0.20-0.31 m/s (Run 1) or 0.44-0.45 m/s (Run 2) of
  cross-track velocity in the direction of the previous leg. Peak error comes
  0.7-1.3 s into the lane: Run 2 18.9 / 29.2 cm, Run 1 up to 13.9 cm.
- **Margins at 1.5 m/s:** tilt max 12.0° (limit 45°), motor command max 0.19
  (hover about 0.12, so it is heavily overpowered), no allocator saturation. Flow
  rate max 2.34 rad/s (`SENS_FLOW_MAXR` 8), quality median 81 (Run 1 83), flow test
  ratio max 0.31 (Run 1 0.10). PX4 speed: Run 1 max 0.45 / p95 0.40, Run 2 1.31 / 1.26.
- **IMUs:** the BMI088 (gyro 6684690) was primary throughout. The BMI270 (3604506)
  read −1.22 (Run 1) / −1.60 (Run 2) °/s mean yaw rate in flight against the BMI088's
  +0.1, the same fault as the trial flights. No xy/z/vxy/heading reset
  in flight.
- **Heading:** no yaw alignment (`cs_yaw_align` 0). EKF heading 1σ 2.4° → 7.9° (Run 1),
  2.4° → 4.5° (Run 2). Run 1's LOC_FIT turn (−3.83°) is only 1.2° more than the
  hover alignment (+2.65° plan turn = −2.65° PX4→arena), so the real drift was small.
- Battery current reads 15 A average (60 A peak), which looks implausible for this
  drone (current-sensor scale?). It is not used in the report.
